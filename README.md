# RetinaReach — Screening workflow prototype

**SIH problem statement 26038** — Explainable AI-assisted diabetic retinopathy screening in rural India  
**Team:** Retinova

RetinaReach is a frontend prototype for a screening and clinical decision-support workflow. It is not a diagnostic device, does not run a trained DR model, and has not been clinically validated. Screening scenarios and overlays are illustrative; qualified clinicians retain responsibility for interpretation and patient management.

## Run locally

```bash
npm ci
npm run dev
npm run build
npm run lint
npm run preview
```

The project uses React, Vite, React Router, and Lucide icons. No backend or authentication service is included.

## Screening workflow

The workspace keeps these nine stages in order: Patient → Capture → Retinal check → Quality → Analysis → Result → Explain → Review → History. Previously visited stages can be revisited from the progress rail. The workflow is a frontend demonstration; there are no real model inference or clinical quality metrics behind the illustrative states.

Patient records are stored in browser `localStorage` under a RetinaReach-specific key and remain across refreshes in the same browser profile. This is local prototype storage, not a protected clinical record system. New screening entries are saved after a review is submitted.

## Implemented behavior and boundaries

- Upload checks accept JPG, PNG, and WebP files up to 15 MB.
- A transparent image heuristic checks for a fundus-like input. It is not a trained or clinically validated retinal classifier.
- Quality status and checks are heuristic demonstration output. No independently validated image-quality model or measured quality scores are present.
- The illustrative screening grade, confidence, and explainability overlays are derived from a deterministic non-clinical image signature. They are not clinical probabilities, diagnoses, or causal evidence.
- The specialist review stage supports confirmation or override before saving the screening entry.
- The Technology page contains planned architecture and an illustrative district simulation; these are not deployed backend services.

## Known limitations and future work

- No API, backend, database, authentication, synchronization, or protected image storage is included.
- Retinal-domain and quality checks need dedicated validation and failure-case evaluation.
- Demo analysis and explainability are illustrative and must not be represented as trained model outputs.
- The quality helper currently returns only GOOD or BORDERLINE for accepted retinal inputs; an UNGRADABLE workflow state is not generated by the current implementation.
- Patient search, editing, richer profiles, and registry filters remain future work.
- No end-to-end screen-reader or clinical usability audit is claimed.
